`astron-collection` is the official command-line client for Astron Collection. It talks to the same API the dashboard uses, so anything you can do in the interface — create projects, deploy applications, provision databases, inspect logs, clean up servers — you can do from a shell, a CI job or a Makefile.

The command surface is generated from the API specification rather than written by hand: **57 command groups and 604 commands**, each one mapping to exactly one API operation.

## Requirements

- **Node.js 18 or newer** — the CLI declares `>=18.0.0` in its `engines` field.
- **A Astron Collection instance you can reach over HTTP** — self-hosted or Astron Collection Cloud.
- **An API key** with the permissions you need. See [Authentication](/docs/cli/authentication).

## Installation

```bash
npm install -g @astron-collection/cli
```

The package installs a single binary called `astron-collection`:

```bash
astron-collection --version
```

`pnpm add -g @astron-collection/cli` and `bun add -g @astron-collection/cli` work the same way.

## Authenticate

```bash
astron-collection auth -u https://panel.example.com -t "$ASTRON_COLLECTION_API_KEY"
```

The CLI validates the key against your instance and stores it for later commands. Environment variables (`ASTRON_COLLECTION_URL` + `ASTRON_COLLECTION_API_KEY`) are an alternative that is a better fit for CI — both are covered in [Authentication](/docs/cli/authentication).

## How commands work

Every command follows the same shape:

```bash
astron-collection <group> <command> [options]
```

| Example | What it does |
| --- | --- |
| `astron-collection project all` | Lists projects (a command with no inputs). |
| `astron-collection application one --applicationId <applicationId>` | Reads a single application. |
| `astron-collection postgres create --name <name> --environmentId <environmentId>` | Creates a database. |

Flags and behaviour:

- **Flags mirror the API inputs**, written in camelCase: `--environmentId` is sent as `environmentId`. The [command reference](/docs/cli/reference) lists them per command.
- **Required flags** (marked *Yes* in the reference) abort the command when missing — commander refuses to run it. Everything else is optional, and anything you leave out is **omitted from the request entirely**, so the server applies its own default.
- **Booleans** are passed without a value: `--enableDockerCleanup`. They are only sent when you include them.
- **Numbers** are converted before they are sent, so `--port 5432` reaches the API as a number, not a string.
- **Every command accepts `--json`** to print the raw API response instead of the formatted output.

### Help

```bash
astron-collection --help                    # groups
astron-collection application --help        # commands in a group
astron-collection application create --help # options of one command
```

Running `astron-collection` or `astron-collection <group>` without a command prints the same help, and `astron-collection --help` is safe to paste into any script.

## Output and exit codes

| Situation | What you get |
| --- | --- |
| Default | The response, pretty-printed as JSON with two-space indentation. Plain strings are printed as-is, and an empty response prints `OK`. |
| `--json` | The raw API payload, unformatted. |
| Failure (bad key, unknown resource, network error) | The error message on stderr and **exit code 1**. |

Because failures are non-zero exits, the CLI drops straight into pipelines: `astron-collection application deploy --applicationId "$APP_ID" && echo deployed`.

## How requests are made

The CLI calls the public API directly, so you can reproduce any command by hand:

- **Endpoint** — `{url}/api/trpc/{group}.{command}`, for example `POST /api/trpc/application.create`.
- **Authentication** — an `x-api-key` header with your key.
- **Reads** (`GET`) pass the inputs as a single URL-encoded `input` query parameter; **writes** (`POST`) send `{ "json": { ... } }` as the body.

This is the same contract described in the [API reference](/docs/api), which is useful when the CLI does not expose something you need.

## Quick start

Create a project, add an environment, wire up a Git application and deploy it:

```bash
# 1. Point the CLI at your instance
astron-collection auth -u https://panel.example.com -t "$ASTRON_COLLECTION_API_KEY"

# 2. Look around
astron-collection project all
astron-collection server all

# 3. Create a project, then an environment inside it
astron-collection project create --name my-project --description "My first project" --env production
astron-collection environment create --name production --description "Production" --projectId <projectId>

# 4. Create an application in that environment
astron-collection application create --name my-app --environmentId <environmentId>

# 5. Connect the Git repository it should build from
astron-collection application save-github-provider \
  --applicationId <applicationId> \
  --githubId <githubId> \
  --owner <owner> \
  --repository <repository> \
  --branch main \
  --buildPath / \
  --triggerType push

# 6. Deploy, then follow the deployment
astron-collection application deploy --applicationId <applicationId>
astron-collection deployment all --applicationId <applicationId>
astron-collection deployment read-logs --deploymentId <deploymentId>
```

<Callout type="info">
	Identifiers such as `<projectId>` are placeholders for values returned by a previous command.
	`astron-collection project all --json` prints the raw payload so you can pull them out with `jq`.
</Callout>
